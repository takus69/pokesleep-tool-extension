# 料理エナジープランナー UC-1 設計案

Refs [#74](https://github.com/takus69/pokesleep-tool-extension/issues/74)、親 [#67](https://github.com/takus69/pokesleep-tool-extension/issues/67)。2026-10-04時点のレビュー用設計。未決事項は第9節に集約し、合意済みと提案を区別する。

## 1. 目的

事前備蓄と期間中の編成から、指定料理を目標回数作れるか、料理の期待エナジーはいくらかを判断する。食材・鍋拡張を確保した残りの編成量を、利用者が選ぶ料理チャンス担当へ配分する。

- 初期対象は1面待ち。期間合計の期待食材量で成立を判定する。各食時点の在庫・スキル発動順序・連続稼働は保証しない。
- 同一個体は複数食材・複数役割を兼ねる。個体の実際の編成日数を一度だけ数え、その日数で生じる全ての対応済み出力を利用する。
- 自動最適化、複数計画保存・比較、きのみ・直接エナジースキルは対象外。料理チャンスの数式は #79 で別途合意する。
- 基本の公開単位はUC-1全体。#83・#84の2・3面待ちは後続公開へ回せる。子Issueは実装・developマージ単位。
- #74の完了条件は9項目・モック・上流境界のレビュー合意。設計案を作っただけでは受入済みにしない。

## 2. 入力仕様

### 計画の入力

| 項目 | 単位・制約 | 決定状況 |
|---|---|---|
| 期間 | 日数 D、正の整数 | 5日・7日などを扱う。整数単位は提案 |
| 編成枠 | S、1〜5の整数 | 初期値5の提案 |
| 目標料理 | カテゴリ・レシピ・レシピレベル | 利用者が指定、1面待ちから開始 |
| 目標料理回数 | N、0〜3Dの整数 | 合意済み |
| 初期備蓄・バッグ上限 | 食材別の整数個数・上限 | 全食材を合算して容量検証。共通の備蓄を一度だけ保持 |
| 担当個体と実編成日数 | ボックス個体ID、日数 d_i | 小数入力案。0≦d_i≦D。同じ個体は一行に統合 |
| 鍋 | 基本容量、必要鍋拡張回数、担当個体 | 必要回数は手入力。担当の発動期待値との比較を表示 |
| 料理チャンス | 複数担当個体と追加配分日数、配分方式 | 複数個体は合意済み。追加配分方法は第9節 |
| 追加投入 | 平均食材エナジー | 空きを満たす食材がある前提で合意済み |
| 曜日条件 | 開始曜日、日曜料理回数 | 第9節の提案。Nに含む回数であり別加算しない |

個体ごとに役割ラベルは複数選べるが、役割ラベルによって食材・スキル出力を重複計上しない。追加配分は既存日数へ加算し、その個体の全出力を再計算する。鍋担当に必要な参考日数を表示し、編成日数は利用者が確定する。参考日数を変更せず勝手に割り当てない。

役割はその個体の実際の食材・対応スキルから選択可能にする。ラベルを付けるだけで別のメインスキルを発動できる扱いにはしない。例えば食材と鍋は兼任できても、料理チャンスを持たない個体を料理チャンス担当として追加できない。

### 元ツールから取得

- `PstPokeBox`：保存済み個体と安定したID。参照専用。個体は現在のレベル・進化・スキルレベルで計算することが合意済み。
- `PstStrenghParam`：フィールド・フィールドボーナス、イベント、睡眠・回復・タップ頻度、キャンプ等の計算環境。読み取った条件のスナップショットを使い、計算用コピーで `period=24`、`level=0`、`evolved=false`、`maxSkillLevel=false` を設定する。元の保存値は書き換えない。
- ランキング専用の条件加工は流用しない。料理用の読み取りadapterから明示的に条件を構成する。
- 入場時と「元ツールの条件を再読込」で更新。計算中の条件・個体一覧を固定し、変化時は結果を「条件変更・再計算が必要」にする。
- 未知イベント・能力・必須条件がある場合は、影響する出力を計算不可にする。未対応効果を無言で無視して成立と表示しない。

レシピ材料とレシピ基礎エナジーの一覧は固定上流の `src/data` に見当たらず、既存のポケモン・イベントJSON同期の対象でもない。新たなデータ出典・更新方法・ライセンスを #75/#76 の着手前に確定する。未取得レシピを名前だけで推測しない。

## 3. 処理ロジック

### ブラウザ非依存の処理

`src/domain` に、検証済み計画、公式の日次能力、レシピ定義を渡す。DOM・Chrome Storage・上流保存形式を持ち込まない。

1. 入力・同一個体ID・容量・日数を検証する。総編成量 `T=Σd_i`、上限 `S×D`。個体上限と総量上限を両方確認する。
2. 公式計算を各個体24時間条件で実行し、食材別日次取得量 `q_ij`、スキル発動期待値 `r_i`、対応スキル効果を取得する。独自の個体能力式を作らない。
3. 食材jの必要量 `R_j=N×レシピの材料数_j`、利用可能量 `A_j=備蓄_j+Σ(q_ij×d_i)`。全て `A_j≧R_j` なら食材面で成立。負の差を不足数として表示する。
4. 参考必要日数は「他個体の供給を固定して、この個体に何日必要か」の値 `max_j(max(0, R_j−備蓄_j−Σ_{k≠i}(q_kj×d_k))/q_ij)`。この個体の現在の日数分は引かない。不足食材の率が0なら解消不可。最適解とは呼ばず、丸めた表示値で成立判定しない。
5. 鍋の成立を別判定し、食材成立と併せて総合成立を表示する。単純な「期間の鍋容量総和≧材料総和」では一食の必要容量を確認できない。通常／日曜の各料理に必要な拡張発動をどう割り当てるかは #77 の合意事項。未確定の段階で全体成立にしない。
6. 残り編成量 `S×D−T` と各料理チャンス担当の個体残余 `D−d_i` を表示。追加日数の総和は残り以下。発動期待値 `Σ(r_i×最終d_i)` を一度だけ集計し、役割兼任分も含める。
7. #79で定義する配分モデルへ、食数・曜日・スキル効果別発動期待値を渡す。スキルレベルが異なる担当の発動回数を、同一の上昇量として一括処理しない。
8. レシピエナジー、追加投入エナジー、大成功による増分を分け、同一の曜日・フィールド条件で合算する。失敗時には目標N回のエナジーを「実現可能な期待値」として表示しない。

日次率×日数の線形近似を使う。編成変更で回復・おてつだいボーナス等が変化する逐次再計算は対象外。元ツールから引き継ぐ環境条件を全担当に適用する仮定を画面に表示する。

### 上流能力の出力範囲

現行 `PokemonCalculationPort` は通常のおてつだい食材と `skillCount` 等を返す。`PokemonStrength.calculate().ingredients` に食材獲得スキルの食材は含まれない。食材ゲット・食材セレクト等について、公式の数量出力・対象食材を使う専用adapterを設計し、通常食材と合算できる対応一覧を契約テストで固定する。`ingStrength` や `skillStrength` から個数を逆算しない。未対応スキルは該当する食材出力を計算不可として明示する。

鍋拡張・料理チャンスには `skillValuePerTrigger` 等が必要で、現在のポートには未公開。ランキングの既存契約を維持し、必要な型付き出力を追加するか料理専用ポートを設ける。上流が推計する料理スキルのエナジーを再利用して二重計上しない。

### 後続の2・3面待ち

同じ初期備蓄から、選んだカテゴリそれぞれを別の週として評価する。備蓄を枝間で消費し合わず、同一食材は各枝で使える。全枝で同じN回を目指し、カテゴリ決定後の個体・日数は枝ごとに変更できる。結果は枝ごとに表示する。カテゴリ確率で平均化せず、一つでも未成立なら「全候補で成立」としない。

## 4. 出力仕様

表示順は、総合判定→食材→編成量→鍋→料理チャンス→料理エナジーとする。

- 食材：材料別の必要量、備蓄、期間取得期待量、合計、過不足。担当別の日次取得量・実日数・参考必要日数。
- 編成：使用／上限の枠日、残り、担当別の日数上限、未配分。枠日は「1個体を1日編成」で説明する。
- 鍋：一食のレシピ材料数、基本容量、必要拡張回数、発動期待値、判定。詳細な容量割当は #77。
- 料理チャンス：担当別の発動期待値、合計、方式、期待大成功回数・確率。仕様未決定時は空欄と理由を表示する。
- エナジー：レシピ通常分、追加投入通常分、大成功増分、合計。対象食数・日曜食数・ボーナス条件を併記する。
- 状態：未計算、読込中、計算中、成立、条件不足、計算不可、結果が古い。数値が出ない状態を0と表示しない。

不成立時は不足要因と食材・編成の中間結果を表示する。実際に作れる回数の最大化は #69 と区別し、初版では算出しない。

## 5. 画面仕様・モック

[画面モック](cooking-planner-mock.html)を構成案の正とする。元ツールの黄色系ヘッダー、青いタブ選択線、下線付き入力、青灰色の見出し帯に合わせた。食材アイコンは固定上流のMIT素材を静的SVGへ変換して利用する。

モックはドキドキこわいかおパンケーキ（デザート・ドリンク）を使う。一食はエッグ24・トマト29・ミツ32・カボチャ18、計103個。Lv60エナジー73,793、21食の通常分1,549,653は [Game8](https://game8.jp/pokemonsleep/733807) のレシピ情報（2026-10-04確認）による参考値で、フィールド・イベント・大成功加算前。これはモックの出典であり、本番レシピcatalogの採用決定ではない。

担当のハピナス・レントラー・フシギバナ・パンプジン・ジバコイル・デデンネ・ウッウについて、日次取得量・発動率は画面レビュー用の設定例で、手持ち個体の公式計算結果ではない。備蓄・供給・必要量と枠日の例示値は整合させる。入力変更による状態遷移を確認できるが、算出は行わない。

- 元画面のランキングと並ぶ上段「料理」タブ。選択中は元の個体計算ペインを一時退避する。元タブへ戻すと元の画面を復元する。
- 上から「目標と条件」「備蓄」「担当の編成」「計算結果」。条件要約から元ツールの設定画面へ移動できる。戻った後の読み直しは明示する。
- 担当行は個体単位。食材／鍋／料理チャンスの兼任を同じ行に表示し、料理チャンス追加日数を分離する。新規担当はボックス選択から追加。
- 1面待ちはレシピ一つ。#83以降はカテゴリ枝のタブと共通備蓄を追加し、同時に複数枝の入力を混ぜない。
- 幅の狭い画面は一列、担当・食材表のみ横スクロール。外側に固定幅を置かない。計算ボタンをキーボード操作でき、状態通知は `aria-live` を使う。
- 空ボックスは担当追加方法を案内。読込中・計算不可は元画面への復帰操作を残す。エラー箇所は入力のそばと結果の先頭に表示する。

## 6. 元ツールとのインターフェース仕様

`src/integration` に料理入力のread-only adapterとタブ連携を集約する。UIは検証済み型付きモデルだけを受け取る。

| 境界 | 最小出力・責務 |
|---|---|
| 入力snapshot | ボックスID/個体、日次用条件、データrevision、未対応理由 |
| 個体能力port | 食材別日次量、発動期待値、スキル種別・効果量、出力対応状態 |
| レシピcatalog | ID、カテゴリ、材料別必要数、基礎エナジー、出典revision |
| タブcontroller | enter/leave、元DOMの退避・復元、設定画面への遷移、unmount |
| 計算結果 | 食材・枠日・鍋・料理チャンス・エナジーの値と個別判定 |

既存 `upstreamRankingTabController` はランキング専用。料理側が別々に元DOMを隠す実装は避け、共通controllerで拡張タブの排他的な表示・復元を管理する。SPA再描画、タブ順変更、元タブクリック、機能OFF、unmountでも復元する。ネイティブの計算条件UIへのクリックはintegrationだけが行う。上流DOMが未知なら追加を中止し、元画面を使えるままにする。

変更するのは拡張タブ・拡張ペイン・一時的な表示状態。元ツールの入力値やボックスを編集しない。adapter/schema変更ごとに実上流fixtureの契約テストを追加する。

## 7. Chrome拡張固有仕様

- `src/features/cooking` を `FeatureModule` として登録する。初期有効値はリリース時に決定。manifest権限・接続先を増やさない。
- SPA対応・有効設定は既存runtimeの仕組みを使用する。domainはChrome APIに依存しない。
- 初版の編集中計画と結果はページ内メモリ。リロードで消えることを表示する案。永続保存と計画比較は #71。元ツール所有キーを保存先に転用しない。
- #74は文書・モックのみ。配布バンドルへの追加やバージョン更新・ストア申請は行わない。

## 8. 例外・エラー時の動作

| 条件 | 表示・停止単位 | 復旧 |
|---|---|---|
| 備蓄の容量超過／負数／非有限値 | 入力エラー。成立計算を停止 | 入力修正 |
| 個体・総編成の上限超過 | 超過日数を表示。勝手に切り捨てない | 日数を修正 |
| 不足食材の取得率0 | 参考日数は「この個体では解消不可」 | 担当または備蓄を変更 |
| 未知レシピ・食材・スキル効果 | 影響した出力は計算不可。総合成立も確定しない | データ対応／拡張更新 |
| 公式計算の失敗 | 対象個体と結果を計算不可。残り個体で成立としない | 条件再読込、問題報告 |
| 個体削除・条件変更 | 古い結果表示を明示、再計算要求 | 再選択・再読込 |
| DOM非互換 | 拡張タブを停止し元画面を復元 | 再読込・更新 |
| 料理チャンス仕様未実装 | 食材結果は表示、確率と総期待エナジーは未計算 | 後続実装 |

ログはadapter名・エラーコード・上流revisionに限定。ボックス全体、個体名、備蓄計画を送信しない。結果の端数表示と内部数値を区別し、期待量の誤差境界は #75 の挙動テストで決める。

### 実装・検証で詰める事項

小数の表示桁、計算停止の許容誤差、ボックス選択UI、ネイティブタブ協調の抽象化、データ更新通知、性能。domainの食材合算・兼任・枝分岐に挙動テスト、上流保存値・能力出力・タブ復元に契約テストを設ける。各実装PRで `npm run verify` とChrome/Edgeのunpacked受入を行う。

順序は #75（食材・編成）→#76（基本エナジー）→#77/#78（鍋・追加投入）→#79/#80/#81/#82（料理チャンス）→#83/#84（2・3面待ち）。#79の仕様合意は前段と並行できる。#74の段階では本番計算やデータschemaを変更しない。
